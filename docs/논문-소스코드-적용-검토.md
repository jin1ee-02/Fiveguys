## 2. ChatEval — 다양한 역할의 토론이 단일 평가자보다 낫다

**논문 핵심 (원문 확인)**
- 발언 방식 3가지를 비교: 차례로 말하기(one-by-one), 동시에 말하기, 동시에 말하고 요약하기. 차례로 말하기가 가장 좋았습니다.
- **같은 역할 프롬프트를 여러 개 쓰면 단일 에이전트와 차이가 없고**, 서로 다른 역할을 줘야 성능이 오릅니다.
- 역할은 3~4개가 최적이고 5개부터 떨어집니다.
- 토론 턴을 늘려도 뚜렷한 향상이 없고 오히려 나빠지기도 합니다(문맥이 계속 길어지기 때문).
- 최종 결과는 다수결(비교 과제) 또는 평균 점수(채점 과제)로 합칩니다.

**반영한 것**

| 논문 내용 | 구현 | 위치 |
|---|---|---|
| 차례로 말하기 | 검사 → 변호사 → 팩트체크 순서로 호출하고 뒤 발언자가 앞 발언을 봄 | `verdict.py` `run_debate` |
| 다양한 역할 | 판사 1명 → **관점이 다른 심사위원 3명**(논리·공감·근거). 같은 루브릭으로 채점하되 꼼꼼히 볼 관점이 다름 | `JUDGE_PERSONAS` |
| 역할 3~4개가 최적 | 심사위원 기본 3명, `VERDICT_JUDGES`로 1~3 조절 | `.env` |
| 평균 점수로 집계 | 6개 점수와 belief를 평균. 요약 문장은 평균에 가장 가까운 심사위원 것 사용 | `aggregate` |
| 턴을 늘려도 이득 없음 | 최대 3라운드 유지, 에이전트에게는 직전 라운드 발언까지만 전달 | `transcript` |

**논문에 없지만 그 한계에서 나온 보완.** 차례로 말하기는 먼저 말하는 쪽이 논점을 정하는 순서 편향이 있습니다(논문이 "동시에 말하기"를 만든 이유). 그래서 라운드마다 첫 발언자를 바꿉니다. 1라운드는 검사, 2라운드는 변호사가 먼저 말합니다.

**반영하지 않은 것**
- *동시에 말하기 + 요약*: 성능이 낮았고 요약 호출이 추가됩니다. 우리 토론은 3라운드 이하라 문맥이 길어지지 않습니다.
- *ChatEval 코드 직접 사용*: AgentVerse 프레임워크와 YAML 설정에 묶여 있고 두 응답 중 나은 쪽 고르기에 맞춰져 있습니다. 양쪽 채점과 반론이 필요한 우리 구조와 달라 구조만 참고했습니다.

**비용.** 심사위원이 3명이 되어 라운드당 호출이 4회 → 6회로 늘었습니다(2라운드 판결 9회 → 13회). 심사위원 호출은 동시에 실행하므로 대기 시간은 거의 늘지 않습니다. 비용이 부담되면 `VERDICT_JUDGES=1`로 되돌릴 수 있습니다.

## 3. Adaptive Stability Detection — 언제 토론을 멈출 것인가

**논문 핵심 (원문 확인)**
- 판사 k명(실험에서는 7명)이 최대 10라운드 토론합니다.
- 라운드 t에서 "정답을 맞힌 판사 수" S^t를 여러 과제에 걸쳐 모으고, 이를 **베타-이항 혼합분포 2성분**으로 모델링해 EM으로 추정합니다.
- 연속한 두 라운드의 추정 분포 사이 KS 거리 D_t가 **0.05 미만으로 2라운드 연속**이면 멈춥니다.
- 공개 코드는 찾지 못했습니다.

**그대로 쓸 수 없는 이유.** 혼합분포를 추정하려면 **여러 과제의 표본**이 필요합니다. 논문의 종료 판정은 평가 세트 전체를 놓고 "이 라운드쯤이면 판정 분포가 안 움직인다"를 보는 것이고, 사용자 한 명의 판결 한 건 안에서는 표본이 판사 수(3~7개)뿐이라 추정할 수 없습니다. 또 "2라운드 연속"은 최대 10라운드를 전제로 하는데 우리는 비용 때문에 3라운드가 한계입니다.

**그래서 둘로 나눠 반영했습니다.**

① **판결 한 건 안에서 (온라인)** — `verdict.py`
논문의 원리인 "판정 분포가 라운드 사이에 움직이지 않으면 멈춘다"를 표본이 작아도 계산되는 형태로 적용했습니다.

```text
각 심사위원의 belief → 의견: B (0.45 미만) / 비슷 / A (0.55 초과)
D = 이번 라운드와 직전 라운드의 의견 분포 사이 KS 거리 (B < 비슷 < A 순서 척도)

종료 = 양 라운드 모두 unresolved 아님
       AND 평균 점수 변화 ≤ VERDICT_STABILITY_DELTA (5점)
       AND 평균 belief 변화 ≤ VERDICT_BELIEF_DELTA (0.1)
       AND D ≤ VERDICT_KS_DELTA (0.34)
```

심사위원이 3명이면 D는 0, 1/3, 2/3, 1 중 하나입니다. 기본값 0.34는 "한 명이 한 칸 움직인 것까지 허용"입니다. 논문의 0.05는 매끄럽게 추정한 분포 기준이라 3명 표본에는 맞지 않아 쓰지 않았습니다.

② **평가 세트 전체에서 (오프라인)** — `scripts/stability.py`
논문 방식 그대로입니다. 베타-이항 2성분 혼합을 EM(E단계 책임도, M단계 L-BFGS-B)으로 추정하고, 잠재 정확도 분포의 CDF 차이로 D_t를 구해 "0.05 미만 2회 연속" 규칙을 재현합니다.

```bash
python -m scripts.evaluate_verdict --stability
```

조기 종료를 끄고 최대 라운드까지 돌린 뒤 라운드별 "정답과 같은 의견을 낸 심사위원 수"로 수렴 라운드를 분석합니다. 온라인 규칙 ①의 임계값이 너무 일찍 또는 늦게 멈추는지 점검하는 용도입니다.

합성 데이터로 구현을 확인했습니다. 분포가 실제로 바뀐 라운드는 D=0.32, 같은 분포에서 뽑은 라운드끼리는 D=0.044와 0.048이 나와 규칙이 4번째 라운드에서 수렴을 판정했습니다. 다만 이 분석은 **라벨된 사례가 수십 개 이상** 있어야 의미가 있습니다. 지금 들어 있는 예시 4개로는 추정이 불안정하다는 경고를 스크립트가 출력합니다.

## 4. AgenticSimLaw — 추론 과정을 전부 볼 수 있게

**논문 핵심 (원문 확인)**
- 검사·변호사·판사가 7턴 구조(모두 발언 → 반박 → 최종 발언 → 판결)로 토론합니다.
- 각 에이전트는 **비공개 전략을 먼저 세우고** 공개 발언을 합니다. 전략은 다른 에이전트와 판사에게 보이지 않습니다.
- 판사는 토론 중간에 belief(예측, 확신도 0~100%, 근거)를 갱신하고 그 변화를 기록합니다.
- 공개 발언, 비공개 전략, 판사 belief, API 메타데이터(토큰 수, 지연)를 **전부 로깅**합니다.
- 비용은 단일 프롬프트의 11~14배입니다.
- 코드는 "공개 예정"이라고만 되어 있고 아직 올라오지 않았습니다.

**반영한 것**

| 논문 내용 | 구현 |
|---|---|
| 비공개 전략 → 공개 발언 | 에이전트 출력이 `strategy` → `text` 순서. 전략은 본인의 다음 라운드에만 전달 |
| 판사는 공개 발언만 봄 | 심사위원 입력에서 전략 제외 (테스트로 확인) |
| 모두 발언·반박·최종 발언 | 라운드마다 `phase`(opening / rebuttal / closing)를 전달하고 단계별 지시를 프롬프트에 명시 |
| 판사 belief 추적 | 심사위원별 belief를 라운드마다 기록하고 화면에 표시 |
| 전체 로깅 | 발언·전략·근거 번호·belief·의견 분포를 판결과 함께 DB에 저장 |
| API 메타데이터 | 판결마다 입력·출력·**캐시된** 토큰 수와 소요 시간을 합산해 `usage`로 반환 |

마지막 항목은 이전 문서에서 "prompt caching 효과 미측정"으로 남겨 둔 문제의 측정 수단이기도 합니다. LLM을 연결하면 판결 화면에 "입력 N토큰(캐시 M)"이 표시되어 공통 prefix 구조가 실제로 캐시에 적중하는지 바로 볼 수 있습니다.

**다르게 한 것**
- *전략과 발언을 한 번의 호출로.* 논문은 별도 호출이지만 호출 수가 두 배가 됩니다. 구조화 출력이 필드 순서대로 생성된다는 점을 이용해 한 호출 안에서 전략을 먼저 쓰게 했습니다.
- *턴 수 고정 대신 조기 종료.* 7턴 고정이 아니라 §3의 규칙으로 2~3라운드에서 멈춥니다. 그래서 "최종 발언" 단계는 최대 라운드에 도달했을 때만 나옵니다.
- *팩트체크 역할 추가.* 논문에는 없습니다. 일상 대화에서는 한쪽 주장과 대화로 확인되는 내용을 구별해 줄 역할이 필요합니다.
- *temperature.* 논문은 토론에 0.7을 썼습니다. 우리는 처음에 모델 기본값을 썼는데, 같은 대화의 점수가 실행마다 5점씩 달라져 10월 8일에 0으로 낮췄습니다(`OPENAI_TEMPERATURE`, 지원하지 않는 모델은 빈 값). 다양성은 역할 차이에서만 얻으며, 그 결과 세 심사위원의 점수가 거의 같아졌습니다.
- *채점 대상.* 논문의 판사는 변론을 듣고 사건을 판단합니다. 우리 점수는 당사자의 표현을 재는 것이라, 변론이 아닌 당사자의 실제 발화만 채점하도록 분리했습니다(AI 활용 설명 5.2 ④).

## 5. LLMediator — AI는 제안만, 결정은 사람이

**논문 핵심 (원문 확인)**
- F1: 격한 메시지를 덜 대립적으로 **다시 쓴 제안**을 보여줍니다. 사용자는 원문 전송 / 제안 전송 / 제안을 고쳐서 전송 중 고릅니다.
- F2·F3: 중재자가 개입할 **메시지 초안**을 만들어 줍니다. 중립을 지키고 당사자의 말을 대신 쓰지 않습니다.
- 격한 메시지 감지는 **키워드 검색**과 **사용자의 수동 요청**이고, 정교한 감지는 향후 과제로 남겼습니다.
- 저자들이 든 위험: 환각, 편들기, 자기 표현 상실, 제안에 대한 과의존과 앵커링.

재작성 프롬프트(원문):
> Reformulate the message to maintain the content, but make it less confrontational and more encouraging for an amicable settlement. Respond directly with the reformulated message, do not explain.

**반영한 것**

| 논문 내용 | 구현 |
|---|---|
| 내용은 유지하고 덜 대립적으로 | `LIGHT_PROMPT`의 대안 규칙. 여기에 "근거 없는 사과·양보·새 사실을 만들지 말 것"을 추가(환각 위험 대응) |
| 원문 / 제안 / 고쳐서 전송 | 이미 원문·대안 전송이 있었고, 이번에 **"고쳐서 보내기"** 추가 — 대안을 입력창에 넣어 수정 후 전송 |
| 사용자의 수동 요청 | **"다듬기 제안 받기"** 추가 — 감지되지 않은 문장도 원하면 대안 3개를 받음 (`force_rewrite`) |
| 중재자 개입 메시지 | 중립적인 제안을 주는 API (`POST /v1/rooms/{id}/mediation`). 진입점이던 쿨다운 창을 10월 8일에 제거해 지금은 화면에서 부를 수 없음 |
| 자기 표현 상실 위험 | 대안을 1개가 아니라 성격이 다른 3개(부드럽게 / 간결하게 / 요청을 분명히)로 제시 |

중재 제안은 논문의 위험 목록을 반영해 제한을 걸었습니다.
- **요청한 사람에게만** 보이고 대화방에는 전송되지 않습니다(테스트로 확인). 논문은 자동 개입 가능성을 논하지만, 두 사람의 사적 대화에 AI가 끼어드는 것은 범위를 넘는다고 판단했습니다.
- 자동으로 뜨지 않고 **사용자가 눌렀을 때만** 호출합니다(비용과 과의존 대응).
- 프롬프트에 "편들지 말 것, 누가 잘못했는지 판정하지 말 것, 당사자의 다음 메시지를 대신 쓰지 말 것"을 명시했습니다.

**논문보다 나아간 부분.** 논문의 감지는 키워드 검색이라 욕설 없는 비꼼("진짜 대단하시네")을 잡지 못합니다. 우리는 감지와 재작성을 한 번의 LLM 호출로 처리하고 문맥을 반영합니다. 기획서 p9의 "비속어뿐 아니라 비꼼, 수동공격적 어투까지"가 이 부분입니다.

## 6. 평가 자료

### AITA-Reddit-Dataset (p23) — 반영

```bash
python -m scripts.evaluate_verdict --aita 경로/aita.csv --top-k 20
```

`title, text, verdict, score` 열을 읽어 score 상위 k개를 판결합니다. 6개 점수를 NTA/YTA/ESH/NAH로 매핑해 커뮤니티 다수결 라벨과 비교합니다.

기획서가 적은 한계가 그대로 남습니다.
- 게시물은 **작성자 한 명의 서술**이라 모든 메시지가 A의 것이고 B의 발언이 없습니다. 양쪽 대화를 전제로 한 우리 파이프라인과 입력 조건이 다릅니다.
- 영어 데이터입니다. 한국어 프롬프트로 영어 게시물을 판결하게 되며, 번역하면 말투 정보가 바뀝니다.
- 다수결 라벨은 중재의 정답이 아닙니다.

따라서 AITA 결과는 참고 지표로만 쓰고, 주 평가는 팀이 라벨링한 한국어 양측 대화(`examples/verdict_cases.json` 형식)로 하는 것을 권합니다. 데이터 파일은 저장소에 넣지 않았습니다. 사용 조건을 확인한 뒤 내려받으세요.

### MELD (p26) — 부분 반영

```bash
python -m scripts.evaluate --meld 경로/dev_sent_emo.csv --limit 200
```

MELD는 7가지 감정 분류이고 우리 온도계는 "표현된 분노·긴장의 강도" 5단계라 라벨이 맞지 않습니다. 비교 가능한 부분만 평가합니다. MELD의 anger·disgust를 양성으로 두고, 온도계가 3단계(분명한 짜증) 이상으로 판정했는지의 precision / recall / F1을 냅니다. 같은 대화의 앞선 발화를 문맥으로 넣습니다. 영어 데이터라는 한계는 같습니다.

### Sentence-BERT 의미 보존 (p26) — 반영

```bash
python -m scripts.evaluate_rewrite --similarity
```

원문과 순화 대안의 문장 임베딩 코사인 유사도를 냅니다. 기본 모델은 한국어 SBERT인 `jhgan/ko-sroberta-multitask`이고 다른 모델을 지정할 수 있습니다. `transformers`와 `torch`가 필요하며 처음 실행할 때 모델을 내려받습니다.

### Google Perspective API (p26) — 대체

**Perspective API는 2026년 12월 31일에 종료되고 신규 사용 신청도 2026년 2월까지만 받았습니다.** 지금은 키를 새로 발급받을 수 없어 기획서의 독성 평가 방법을 쓸 수 없습니다.

대신 두 가지를 넣었습니다.

```bash
python -m scripts.evaluate_rewrite              # 프로젝트 자체 갈등 점수의 전후 비교 (항상 출력)
python -m scripts.evaluate_rewrite --toxicity   # 독립된 한국어 독성 분류 모델의 전후 비교
```

`--toxicity`의 기본 모델은 `smilegate-ai/kor_unsmile`(한국어 혐오·욕설 분류)이고, "문제 없음" 라벨의 확률을 1에서 뺀 값을 독성으로 씁니다. 자체 갈등 점수는 순화를 만든 것과 같은 모델이 채점하므로 독립적인 평가가 아닙니다. 보고서에는 독립 분류 모델 결과를 함께 제시하세요.

> **확인 범위.** `--similarity`와 `--toxicity` 코드 경로는 이 PC에 이미 받아져 있던 다른 한국어 BERT 모델로 실행해 오류 없이 동작하는 것만 확인했습니다. 기본으로 지정한 두 모델은 내려받지 않았으므로 **모델 이름과 라벨 구성(`clean`)이 맞는지는 처음 실행할 때 확인이 필요합니다.** 라벨 이름이 다르면 `--clean-label`로 지정하라는 안내가 나옵니다.

## 7. 반영하지 않은 것

**EmoBERTa (p25).** 화자 이름을 발화 앞에 붙이고 앞뒤 발화를 문맥으로 넣는 RoBERTa 기반 감정 분류 모델입니다. 영어(MELD, IEMOCAP)로 학습되어 한국어 채팅에 쓸 수 없습니다. "화자를 구분해 문맥과 함께 넣는다"는 입력 구성 아이디어는 우리 프롬프트에 이미 들어 있습니다(`recent_messages`의 화자 표시와 `target` 분리). 한국어 로컬 분류 모델이 필요하다면 KcELECTRA 같은 한국어 모델을 감정 강도 라벨로 직접 학습시켜야 하는데, 라벨 데이터가 없어 범위 밖으로 두었습니다.

**Qwen 등 로컬 LLM (p25).** 기획서는 실시간 기능을 로컬 모델로 돌려 비용과 지연을 줄이려 했습니다. 이번 구현은 다른 방법으로 같은 문제를 풀었습니다. Light 통합 호출로 메시지당 1회, 온도계는 0회, 단순 응답은 사전 필터로 0회입니다. 그래도 로컬 모델을 시험하고 싶다면 연결 지점은 하나입니다. `provider.py`의 `structured()`와 같은 시그니처의 클래스를 만들면 됩니다. 단, 현재 어댑터는 OpenAI의 Responses API와 구조화 출력을 쓰므로 로컬 서버가 이를 지원하는지, 한국어 비꼼 감지와 스키마 준수가 되는지는 직접 확인해야 합니다.

**LangGraph (p16).** 토론 흐름은 "역할 3개 → 심사위원단 → 종료 판정"의 단순 반복이라 Python 반복문 40줄로 표현됩니다. 그래프 프레임워크를 넣으면 의존성과 학습 비용만 늘어난다고 판단했습니다. 판결을 백그라운드 작업으로 돌리고 중간 상태를 저장·재개해야 하는 단계가 오면 도입할 가치가 생깁니다.

## 9. 확인한 것과 남은 것

**확인한 것**
- 백엔드 테스트 통과(현재 43개). 심사위원 패널 집계, KS 거리, 발언 순서 교대, 단계 전달, 전략 비공개, 수동 순화, 중재 제안의 비공개성, 토큰 사용량 집계 포함
- 프론트 타입 검사·ESLint·단위 테스트 통과
- 브라우저에서 중재 제안, 수동 다듬기, 고쳐서 보내기, 심사위원 3명 판결 화면을 오프라인 규칙 모드로 구동
- 베타-이항 혼합 추정과 KS 종료 규칙을 합성 데이터로 검증
- AITA·MELD 로더를 같은 열 구성의 작은 예시 파일로 실행

**남은 것**
- 조기 종료 임계값이 적절한지. 실제 모델에서 온도 0으로는 심사위원 3명의 의견이 거의 갈리지 않았습니다
- 심사위원 패널이 판사 1명보다 나은지(`VERDICT_JUDGES=1`과 3을 같은 사례로 비교)
- 실제 AITA·MELD 데이터와 기본 지정 모델로의 평가 실행
- 팀이 라벨링한 한국어 양측 갈등 대화 수십 건 — 위의 모든 평가가 여기에 달려 있습니다
